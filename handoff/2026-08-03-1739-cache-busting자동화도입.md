# cache-busting 자동화 도입 인수인계 문서

작성일: 2026-08-03 (KST)

## 1. 목표

To-Do "cache-busting 전체 에셋 통일 여부 결정"(기존 🔵 보류) 항목을 진행하기로
결정하고, 수동 버전 관리(사람이 `?v=` 값을 직접 올려야 하는 방식) 대신
**콘텐츠 해시 기반 완전 자동화** 방식으로 구현·배포함. 목표는 앞으로 JS/CSS
파일을 수정해도 사람이 버전 번호를 관리할 필요 없이, 브라우저 캐시가 항상
최신 파일을 받아가도록 만드는 것.

## 2. 현재 상태

### (1) 구현 내용 (확인 완료: 코드 작성 + 실행 + 실배포 검증)

- **신규 스크립트 `scripts/inject-cache-busting.js`**: `assets/js/*.js`,
  `assets/css/*.css` 각 파일 내용의 SHA-256 해시(8자리)를 계산해, 이 파일들을
  참조하는 모든 HTML의 `<script src="...">`, `<link rel="stylesheet"
  href="...">`에 `?v=해시`를 자동으로 붙임 (기존 `?v=20260722-2` 같은 수동
  버전 문자열은 제거 후 해시로 교체)
- **대상 HTML**: `index.html`, `coin-detail.html`, `pages/*.html`(8개),
  `coins/coin-*.html`(20개) — 총 30개 파일 전부 적용
- **`generate-coin-pages.yml` 워크플로 수정**:
  - `generate-coin-pages.js` 실행 직후 `inject-cache-busting.js`를 실행하는
    단계 추가
  - 트리거 경로를 `assets/js/**/*.js`, `assets/css/**/*.css`, `index.html`,
    `coin-detail.html`, `pages/**/*.html`, `scripts/inject-cache-busting.js`
    까지 확장 (기존엔 코인 데이터 관련 JS 파일만 트리거 대상이었음)
  - 자동 커밋 시 `git add` 대상에 `coin-detail.html`, `pages/*.html` 추가

### (2) 검증 (확인 완료)

- **멱등성 검증**: 스크립트를 연속 2회 실행 → 1차 30개 파일 갱신, 2차 0개
  파일 갱신 (내용이 그대로면 해시도 그대로라 불필요한 diff가 발생하지 않음을
  코드 레벨에서 확인)
- **정합성 검증**: `?v=`가 중복으로 붙는 버그, 오탈자로 인한 매칭 실패
  케이스 grep으로 확인 — 둘 다 0건
- **문법 검증**: `node -c`로 신규 스크립트 JS 문법 통과, `python3
  yaml.safe_load`로 워크플로 YAML 문법 통과
- **`<script>` 태그 짝 불일치 오탐 확인**: `pages/coins.html`에서 open=7,
  close=6으로 잡혔으나, 원인은 JS 주석 안에 `<script src="...">`라는 설명
  텍스트가 있어서였음(실제 태그 아님). `git show HEAD:`로 이 불일치가 우리
  작업 이전부터 존재했음을 확인해 이번 변경과 무관함을 확인
- **실배포 자동 트리거 실증(가장 중요)**: push 직후 `github-actions[bot]`이
  자동으로 워크플로를 실행해 추가 커밋(`911552f`)을 만든 것을 확인. 이
  커밋의 diff를 확인한 결과 `data-premium`(시트 기반 가격 데이터)만
  갱신됐고, cache-busting 해시는 전혀 건드리지 않음 — 즉 JS/CSS 파일
  내용이 안 바뀌었으니 해시도 그대로 유지된다는 설계가 실제 운영 환경에서
  정확히 작동함을 실증

## 5. 참고 사항

- **백업 브랜치**: `backup-2026-08-03-1728` (기준 커밋: `cec5e48`,
  이번 세션 작업 시작 시점). 이번 작업은 결과가 안정적으로 검증됐고 실배포까지
  정상 확인됐으므로 롤백 필요성은 낮으나, 문제가 생기면 이 브랜치로 되돌릴 수
  있음. 브랜치 정리는 하지 않음(정책상 사용자 명시 요청 시에만 삭제).
- **PAT 토큰**: 같은 세션 내 앞서 사용자가 제공한 토큰을 재사용해 이번
  push 진행. 토큰 값은 응답에 노출하지 않았고 메모리/파일/로그에 저장하지
  않음. push 직후 origin URL을 plain HTTPS로 되돌림.
- **cache-busting 자동화 확장 지점(향후 새 에셋 추가 시 참고)**:
  `scripts/inject-cache-busting.js`의 `ASSET_DIRS` 배열이 `assets/js`,
  `assets/css` 두 디렉토리를 스캔하도록 돼 있음. 새 디렉토리(예:
  `assets/images`처럼 캐시 버스팅이 필요한 다른 정적 자산)가 생기면 이
  배열에 항목만 추가하면 됨. 반대로 특정 HTML 파일을 대상에서 빼고 싶으면
  `collectHtmlFiles()` 함수의 파일 목록 로직을 수정.
- **`generate-coin-pages.js` 템플릿 자체는 건드리지 않음**: 코인 페이지
  생성 시 템플릿에 박히는 `<script src="../assets/js/nav.js?v=20260722-2">`
  같은 하드코딩된 구버전 문자열이 있어도, 그 직후 실행되는
  `inject-cache-busting.js`가 항상 최신 해시로 덮어쓰기 때문에 문제가 되지
  않음. 다만 나중에 템플릿을 읽기 좋게 정리하고 싶다면 하드코딩된
  `?v=20260722-2` 부분을 지워도 되는데, 필수 작업은 아님(현재도 정상 동작).
- **워크플로 트리거 확장 관련 주의**: 이제 `pages/**/*.html` 전체가
  트리거 경로에 포함되므로, `pages/` 안의 정적 페이지(about, contact 등)
  문구만 살짝 고쳐서 push해도 워크플로가 매번 돈다. 코인 페이지 생성
  로직 자체엔 영향 없고(입력 데이터가 안 바뀌면 coins/*.html 결과도
  동일) cache-busting 재계산만 도는 정도라 실질적 부작용은 없으나, Actions
  실행 횟수가 다소 늘어날 수 있다는 점 참고.
