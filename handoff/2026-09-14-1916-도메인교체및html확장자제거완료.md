## 2. 현재 상태

### 확인 완료 (직접 grep/diff/node --check로 검증)

- **도메인 전면 교체**: canonical, og:url, JSON-LD `url`/`item`, robots.txt의
  Sitemap 경로, sitemap.xml의 모든 `<loc>`을 `https://tpwhd8648-tech.github.io`
  → `https://onetroy.co.kr`로 교체. 레포 전체 재검색 결과 잔여 참조 0건
  (단, `handoff/` 폴더 내 과거 기록 문서는 원래 의도대로 건드리지 않음).
- **내부 링크 `.html` 확장자 제거**: `index.html`, `pages/*.html`(8개),
  `coins/*.html`(21개), `coin-detail.html`, `assets/js/nav.js`,
  `assets/js/footer.js`, `assets/js/products.js` 전체에서 내부 링크의
  `.html`을 제거. canonical/og:url/sitemap도 링크와 같은 형태(확장자 없음)로
  통일 — 링크는 깔끔한데 canonical만 `.html`로 남으면 구글이 두 URL을
  별개로 인식해 SEO 신호가 갈릴 수 있어 제가 판단해서 함께 맞춤 (이 판단은
  사용자에게 별도 확인받지 않고 진행함, 문제 있으면 알려주시면 됨).
- **실제 물리 파일명은 그대로 유지**: `coins/coin-*.html` 등 실제 저장된
  파일명은 손대지 않음 — GitHub Pages가 확장자 없는 요청도 같은 파일로
  서빙하는 특성을 이용한 것. `scripts/generate-coin-pages.js`의 파일 쓰기

## 3. 진행 단계 (재사용 가능 메모)

- **도메인/확장자 같은 대규모 링크 치환 작업 시**: 단순 문자열 치환보다
  먼저 "실제 파일 경로 생성 로직"과 "사용자에게 보이는 URL 생성 로직"이
  섞여 있는 파일(`generate-coin-pages.js`처럼 SSG 스크립트)을 반드시
  구분해서, 파일 쓰기 경로(`path.join`, 실제 `fs.writeFileSync` 대상)는
  건드리지 않고 URL 생성 변수만 골라서 고쳐야 함. 이번에 `\.html(?=["'
  \`?#])` 같은 lookahead 정규식으로 일괄 치환했는데, 이 방식을 그대로
  `generate-coin-pages.js`에 썼으면 실제 파일 저장 경로까지 깨질 뻔했음
  → 이 파일만 수작업으로 개별 라인 수정.
- **정규식 일괄 치환 전 오탐 여부 반드시 사전 grep**: `'.html'`처럼 순수
  리터럴 비교(예: `name.endsWith('.html')`)가 있는지 먼저 확인해야
  일괄 치환이 로직을 깨뜨리지 않음. 이번엔 대상 파일들에 그런 패턴이
  없음을 확인 후 진행함.
- **링크 스킴을 바꾸면 클라이언트 사이드 "현재 페이지 판별" 로직도 같이
  점검**: `location.pathname` 기반으로 활성 메뉴를 판별하는 코드가 있으면
  확장자 변경의 영향을 받으므로 반드시 같이 찾아서 정규화해야 함.

  ".html 확장자 제거" 두 가지를 마무리한 것입니다.
- **canonical/sitemap도 확장자 없이 통일한 판단 근거**: 링크만 확장자를
  없애고 canonical/sitemap을 그대로 두면 구글이 "same content, 2 URLs"로
  인식해 인덱싱 신호가 분산될 수 있음. 단일 URL 형태로 통일하는 쪽이
  안전하다고 판단해 사용자 재확인 없이 진행함 — 방향이 다르다고 판단되면
  canonical만 다시 `.html` 붙은 형태로 되돌리는 것도 가능(파일 몇 개만
  수정하면 됨, 이번처럼 대규모 작업 아님).
- **`.html` 확장자가 남아있어도 무방한 곳**: `scripts/generate-coin-pages.js`,
  `scripts/inject-cache-busting.js`의 파일 경로/파일명 관련 코드, 실제
  `coins/*.html` 물리 파일명 자체 — 전부 의도적으로 유지함.
