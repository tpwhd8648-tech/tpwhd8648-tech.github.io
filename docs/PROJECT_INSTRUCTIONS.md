# 프로젝트 작업 지침 (Claude용)

이 문서는 `tpwhd8648-tech.github.io` 레포 작업 시 Claude가 따라야 할 워크플로우의
원본(단일 진실 소스)이다. 여러 계정에서 동일한 작업 지침을 쓰기 위해, 각 계정의
"프로젝트 지침" 칸에는 이 문서를 가리키는 짧은 안내만 두고, 실제 규칙은 여기서 관리한다.

이 문서를 수정하면 별도 계정 설정 변경 없이 모든 계정에 다음 대화부터 반영된다.

## 0. 공통: 모든 작업의 첫 단계 — 항상 먼저 실행

사용자가 코드 수정/확인 요청을 하면, 별도 요청 없이 항상 먼저 아래 명령으로 가볍게
받아온 뒤 작업을 시작한다:

```
git clone --filter=blob:none --no-checkout --depth 1 https://github.com/tpwhd8648-tech/tpwhd8648-tech.github.io.git tpwhd8648-tech.github.io && cd tpwhd8648-tech.github.io && git sparse-checkout init --cone && git sparse-checkout set --no-cone '/*' '!/images' && git checkout
```

(`images` 폴더는 용량만 크고 코드 작업엔 불필요하므로 제외)

사용자에게 확인/선택을 요청할 때는 버튼형 선택지(ask_user_input 류) 도구를
사용하지 않고 일반 텍스트로 직접 질문한다. 버튼 선택지에서 한글 텍스트가
깨지는 인코딩 현상이 반복적으로 발생했기 때문이다.

## 1. 새 채팅 시작 시 — "할일뭐야?" 같은 질문을 받으면

할일 목록 정리 시 **대분류(주제)를 1차 기준**으로 묶고, 각 항목 줄 앞에는
**색깔 이모지(긴급도) + 담당자 이모지**를 함께 표시한다.

**대분류 (5종)**:
- 🔍 SEO — 검색 노출, 메타태그, 구조화 데이터, robots.txt, sitemap, 페이지 속도 등
- 🛍️ 상품 데이터 — 코인 스펙(중량/순도/발행처 등), 시트 데이터, 사업 정보(주소/연락처)
- 🎨 UI/UX — 디자인, 레이아웃, 뱃지, 배너, 탭, 애니메이션
- ⚙️ 기능/인프라 — 검색 기능, 로딩 속도, 코드 정리, 페이지 삭제, 데이터 연결
- 📋 운영/프로세스 — 작업 우선순위, 문서/양식 규칙, PROJECT_INSTRUCTIONS 자체

**색깔 이모지 (긴급도, 각 줄 앞에 표시)**:
- 🔴 긴급 / 즉시 처리
- 🟡 일반 작업
- 🔵 보류
- ⚪ 사실 확인
- 📢 마케팅 / 노출

**작성 예시**:

```
### 🔍 SEO
- 🔴 🤖 (예시) 긴급한 SEO 버그 수정
- 🟡 🤖 관련 코인 섹션 추가
- 📢 👤 구글 서치 콘솔 데이터 확인

### 🎨 UI/UX
- 🟡 🤖 카테고리 배너 디자인 방향 결정
- 🟡 🤖 뱃지 shimmer 애니메이션 제거 → 정적 뱃지로 교체

### 🛍️ 상품 데이터
- ⚪ 👤 서울 본점 주소·전화번호 실제 정보 확인

### ⚙️ 기능/인프라
- 해당 없음
```

(🤖 = Claude 처리 가능 / 👤 = 사용자 직접 액션 필요)

**대분류 정리 시 주의**:
- 5개 대분류는 항목 유무와 무관하게 항상 전부 나열한다. 한 대분류 안에 항목이
  1개뿐이어도 소제목(`### 🔍 SEO` 등)은 생략하지 않는다 — 나중에 같은 대분류에
  항목이 추가될 때 구조가 흔들리지 않도록 일관되게 유지한다.
- 해당 대분류에 미해결 항목이 0개인 경우에도 소제목은 생략하지 않고, 소제목
  아래에 `- 해당 없음`이라고 명시한다. 소제목 자체를 빼버리면 "정말 할 일이
  없어서 생략한 것"인지 "작성 중 깜빡하고 빠뜨린 것"인지 다음 세션이 구분할
  수 없기 때문이다.
- 항목 하나가 여러 대분류에 걸치는 경우(예: SEO와 UI/UX 둘 다 관련) 더 핵심적인
  대분류 하나에만 넣고, 필요하면 항목 설명에 다른 대분류와의 연관성을 괄호로
  짧게 덧붙인다. 중복 등재하지 않는다.



0번 실행 후, 레포 안 `/handoff/` 폴더(파일명 형식: `날짜-시간(HHMM)-주제.md`)에서
파일명 기준 가장 최근(날짜+시간 순) **3개** 파일을 모두 읽는다.

- 최신 파일의 To-Do를 기준으로 삼되, 이전 2개 파일과 교차 확인한다.
- 이전 문서에 있던 항목이 최신 문서에서 빠져 있을 경우, 해당 항목이 **명시적으로
  종결(완료/취소/보류 등) 처리**된 기록이 없으면 미해결로 간주하고 목록에 다시 포함한다.
- 최신 문서에서 명시적으로 종결된 항목은 되살리지 않는다.

해당 폴더나 파일을 찾지 못하면 사용자에게 위치를 물어본다.

## 2. 코드 수정 요청 시

0번 실행 후, 한쪽만 고치고 다른 연관 파일을 놓치는 실수를 막기 위해, 별도 요청
없이 문법오류·함수/변수명 불일치·id-class 충돌·명백한 논리 오류를 grep/view로
빠르게 체크한 뒤 전달한다.

**개선 제안 시 영향도 명시**: 코드 수정이나 개선안을 제안할 때는 항상 예상 영향도를
`[영향 높음]` / `[영향 보통]` / `[영향 낮음]` 중 하나로 함께 표시하고, 한 줄로
이유를 덧붙인다.

- `[영향 높음]` — 미수정 시 기능 오작동, SEO 직접 손실, 또는 사용자에게 잘못된
  정보가 노출되는 경우
- `[영향 보통]` — 현재도 동작은 정상이나 개선 시 코드 품질·유지보수·성능이
  의미 있게 나아지는 경우
- `[영향 낮음]` — 이미 동일한 안전장치가 존재하거나 체감 차이가 미미한 경우

영향도를 먼저 파악해야 작업 우선순위를 올바르게 판단할 수 있다. 문제의 심각성을
과장하거나 축소하는 것 모두 피한다.

## 3. GitHub 토큰을 받았을 때 — push 워크플로우

사용자가 채팅에 `github_pat_...` 형태의 토큰을 붙여넣으면:

1. 토큰으로 해당 레포에 대한 읽기/쓰기 권한을 조용히 확인한다 (화면에 토큰 값을
   다시 출력하지 않음).
2. 코드 수정이 끝나면 변경 사항을 요약해서 보여주고, 반드시 사용자에게
   "푸쉬해줘" 같은 명시적 확인을 받은 후에만 push한다. 확인 없이 자동으로
   push하지 않는다.
3. push 후에는 `git log` 또는 `git ls-remote`로 반영이 잘 됐는지 확인하고,
   커밋 해시와 결과를 사용자에게 보고한다.
4. 토큰은 절대 메모리(memory_user_edits)나 파일, 로그에 저장하지 않는다.
   해당 세션의 작업에만 사용하고 응답에 다시 노출하지 않는다.

## 3-1. 위험도 높은 수정 전 — 백업 브랜치 생성

여러 파일에 걸친 수정, 되돌리기 어려운 구조 변경, 또는 사용자가 명시적으로
"백업해두자"고 요청하는 경우, 실제 코드 수정을 시작하기 전에 별도 요청 없이
먼저 백업 브랜치를 만든다. 단순 오타 수정이나 한두 줄짜리 변경까지 매번 만들
필요는 없다.

**예비용 레포(fork)는 사용하지 않는다** — GitHub Pages가 fork에서도 별도로
사이트를 배포해버려 duplicate content SEO 리스크가 생기기 때문에, 과거 세션에서
이미 검토 후 기각된 방식이다. 브랜치만 사용한다(GitHub Pages는 `main` 브랜치만
빌드/배포하므로 다른 브랜치는 라이브 사이트에 영향 없음).

**절차**:
```
git branch backup-YYYY-MM-DD-HHMM origin/main   # KST 기준, TZ='Asia/Seoul' date '+%Y-%m-%d-%H%M'
git push origin backup-YYYY-MM-DD-HHMM
```
- 브랜치명 타임스탬프는 핸드오프 파일명과 동일하게 KST로 통일한다.
- push 후 `git ls-remote origin refs/heads/backup-...`로 원격 반영을 확인한다.

**롤백이 필요할 때** (반드시 사용자 확인 후 실행, 임의 판단으로 먼저 실행하지 않음):
```
git checkout main
git reset --hard backup-YYYY-MM-DD-HHMM
git push origin main --force
```
- `--force` push는 그 사이 쌓인 커밋들을 `main` 히스토리에서 제거한다(백업
  브랜치 자체에는 남아있으며, `git reflog`로도 복구 가능하므로 데이터 유실은
  아니지만 되돌리기 전 항상 사용자에게 재확인한다).
- 롤백 완료 후 GitHub Actions 재빌드 → GitHub Pages 재배포까지 보통 1분
  이내 소요된다.

**오래된 백업 브랜치 정리**: 특별히 자동 정리하지 않는다. 브랜치가 많아져도
GitHub Pages 배포나 저장소 동작에 영향이 없으므로, 사용자가 명시적으로
정리를 요청할 때만 삭제한다.

## 4. 작업 마무리 시 — "인수인계 만들어줘" 요청을 받으면

handoff-doc 스킬(`/mnt/skills/user/handoff-doc/SKILL.md`)의 문서 구조(목표/현재상태/
진행단계/To-Do/참고사항 5개 섹션)와 작성 유의사항은 그대로 따른다.

**단, To-Do 섹션(4번)은 스킬의 체크박스(`- [ ]`) 양식 대신 이 문서 섹션 1의
대분류(주제) + 색깔(긴급도) + 담당자(🤖/👤) 양식을 우선한다.**

**To-Do 작성 시 누락 방지:** 새 인수인계 문서를 작성할 때도 섹션 1의 교차 확인 규칙을
동일하게 적용한다. 즉, 직전 2개 핸드오프 문서를 확인해서 이전 문서에 있던 미해결 항목이
종결 표시 없이 빠져 있으면 새 문서의 To-Do에 다시 포함한다.

**제안 항목 누락 방지:** 해당 세션에서 Claude가 "하면 좋을 것 같다"고 제안했지만 바로
진행하지 않은 항목은 🤖/👤 구분해서 To-Do에 명시적으로 포함한다. 제안만 하고
인수인계에 빠뜨리지 않는다. 여러 항목을 하나로 뭉뚱그려 "보류 중"으로만 처리하지 말고,
실행 주체(🤖/👤)와 구체적인 작업 내용을 분리해서 각각 항목으로 작성한다.

다만 **파일명 규칙은 이 문서가 우선한다**: 스킬 파일에 적힌 형식과 다르더라도,
항상 `YYYY-MM-DD-HHMM-주제.md` (날짜+시간(HHMM, 24시간제)+주제) 형식을 사용해
`/handoff/` 폴더에 저장한다. 같은 날 여러 작업을 처리할 수 있어 시간까지 포함해야
파일명이 겹치지 않고 작성 순서가 명확해지기 때문이다.

**타임스탬프는 반드시 한국시간(KST, UTC+9) 기준으로 통일한다.** 작업 컨테이너는
UTC로 동작하므로, bash의 `date` 명령을 그냥 쓰면 UTC 시각이 나와 날짜가 하루
어긋날 수 있다. 파일명에 쓸 날짜+시간을 구할 때는 아래처럼 명시적으로 KST로
환산해서 얻는다:

```
TZ='Asia/Seoul' date '+%Y-%m-%d-%H%M'
```

날짜(YYYY-MM-DD)와 시간(HHMM)을 서로 다른 방법(예: 대화 맥락상 "오늘 날짜"는
KST로 알고 있으면서 시간만 별도로 UTC `date` 명령으로 구하는 식)으로 섞어서
조합하지 않는다 — 한쪽은 KST, 한쪽은 UTC가 되어 날짜·시간이 어긋나는 사고가
실제로 있었다 (2026-06-21 관련 핸드오프 문서 3건의 날짜/시간 오기, 이후 수정됨).

**백업 브랜치 존재 여부 명시:** 이번 세션에서 섹션 3-1 절차로 백업 브랜치를
만들었다면, 브랜치명과 어느 커밋(작업 시작 시점) 기준인지를 참고 사항(5번)에
반드시 남긴다. 다음 세션이 롤백 필요 여부를 판단할 때 참고할 수 있어야 한다.

이번 세션에서 진행한 작업 내용, 변경된 파일 목록, 남은 작업, 다음 세션에서 참고할
사항을 포함한다.

**To-Do 섹션은 섹션 1의 대분류(주제) + 색깔 이모지(긴급도) + 담당자 양식으로
작성한다.** 체크박스(`- [ ]`) 대신 대분류 소제목 아래에 색깔 이모지와 🤖/👤
담당자 아이콘을 붙여 항목을 작성한다. 예시:

```
### 🔍 SEO
- 🟡 👤 카테고리 배너 디자인 방향 결정

### ⚙️ 기능/인프라
- 🔴 👤 브라우저에서 뱃지 노출 확인

### 🎨 UI/UX
- 🟡 🤖 footer.js 더미 데이터 정리
```

## 5. 새 상품(코인) 추가 요청 시 — 사진을 받으면 아래 순서로 한 번에 처리

2026-11-16 "2027 캥거루" 추가 때 확립한 절차다. 사용자는 보통 코인 앞·뒷면 사진 2장을
보낸다. 사진이 안 보이면(첨부 누락) 먼저 다시 요청한다.

1. **사진 확인**: 연도·중량·순도·액면가·발행처(마크)를 사진에서 읽는다. 사진에서 확인한
   값과 다른 코인에서 옮겨온 값(직경·두께 등)을 구분한다.
2. **이미지 저장** (`images/products/연도/{slug}.png`, 뒷면은 `{slug}-back.png`):
   - 주 도안(동물·상징이 있는 면) = `{slug}.png`, 초상·액면가 면 = `-back.png`.
   - 규격은 1200×1200 RGB 흰 배경. 흰 배경 기준으로 코인 영역을 크롭 → 긴 변 1110px로
     리사이즈 → 1200×1200 캔버스 중앙에 붙인다(Pillow).
   - `images/`는 sparse-checkout에서 제외돼 폴더가 없다. `mkdir -p`로 만들고, 커밋할 때는
     `git add --sparse`를 쓴다.
3. **`assets/js/coin-data.js`의 IMAGE_MAP에 항목 추가**: `keywords[0]`은 반드시 "연도 + 한글
   정식명"(예: `2027 캥거루`). 영문 키워드도 함께 넣는다.
4. **`assets/js/coin-descriptions.js`에 항목 추가**: keywords는 IMAGE_MAP과 동일하게. `detail`은
   같은 시리즈의 기존 설명을 바탕으로 쓰되 확인되지 않은 사실(기념 문구 등)은 넣지 않는다.
   사진·공식 자료로 확인하지 못한 specs가 있으면 `verified: false`로 둔다. (2026 캥거루처럼
   specs 줄이 중복되는 항목은 Edit 앵커가 겹치므로, 삽입 위치 바로 뒤 항목의 `keywords` 줄을
   앵커로 쓴다.)
5. **구글 시트("상품" 탭) 붙여넣기용 데이터 제공**: 컬럼 순서는
   `상품명 / brand / category / premium / available / same_day / visible / order / image`
   (탭 구분). 사용자는 작업 전에 현재 시트 내용을 먼저 붙여준다. 시트가 없으면 먼저 붙여달라고
   요청한다.
   - **항상 시트 전체를 복붙용으로 돌려준다**: 새 상품 추가뿐 아니라 기존 행의 값 수정(프리미엄·
     재고·당일 출고·visible·order 변경, 행 삭제 등) 요청에도, 한 행만 주지 않고 **전체 행을
     A2부터 통째로 붙여넣을 수 있는 탭 구분 코드블록**(헤더 제외)으로 돌려준다. 사용자가 시트에서
     셀을 하나씩 고치지 않고 전체를 덮어쓰게 하려는 것이다.
   - 새 행을 넣으면 order를 처음부터 연속 번호로 다시 매긴다. 코드블록 뒤에는 바뀐 부분(추가·변경된
     행과 값)만 짧게 요약한다.
   - 돌려주기 전에 검증한다: 모든 행이 9개 컬럼, order가 1부터 연속, premium이 숫자,
     available·same_day가 TRUE/FALSE, visible이 all/main/coins, 상품명이 `coin-data.js`
     키워드와 매칭되고 image 경로가 IMAGE_MAP·레포 이미지와 일치, 상품명 중복·앞뒤 공백 없음.
   - 시트의 상품명에 코드의 keywords 문자열(예: `2027 캥거루`)이 들어 있어야 한다. 시트 행이
     없으면 `generate-coin-pages.js`가 해당 코인을 건너뛴다.
   - 사용자가 주지 않은 값(프리미엄·재고·당일 출고·노출)은 임시값으로 채우고 **임시값임을
     반드시 명시**한다.
   - **visible 값의 의미** (`generate-coin-pages.js`의 `renderIndexGrid`/`renderCoinsGrid` 기준):
     `all` = 메인 "최신 상품 확인하기" + 코인 목록 둘 다, `main` = 메인만, `coins` = 코인 목록만.
     새 상품을 메인에도 보이게 하려면 `all`로 준다(2027 캥거루를 `coins`로 줘서 메인에
     안 나왔던 사례가 있음). 사용자가 노출 위치를 말하지 않으면 `all`을 기본으로 하고 값을
     밝힌다. 메인은 `available`이 TRUE인 상품을 먼저, 그다음 `order` 순으로 정렬한다.
   - 시트 값(visible·프리미엄·재고 등)을 고친 뒤에는 Actions를 다시 실행해야 정적 페이지에
     반영된다.
   - 사용자가 순서를 지정하면(예: "3번으로") 나머지 행의 order를 모두 밀어 반영한다.
6. **검증·커밋**: `node --check`로 두 JS 파일 문법을 확인하고 커밋한다(트레일러 포함).
7. **푸시**: 섹션 3 규칙대로 사용자의 명시적 "푸쉬해줘" 확인 뒤에만. 원격에 Actions 자동 커밋이
   쌓여 있을 수 있으므로 푸시 전에 `git fetch --depth=1 origin main`으로 확인한다.
8. **Actions 실행**: 사용자가 시트를 수정한 뒤 "액션도 해줘"라고 하면
   `generate-coin-pages.yml`을 수동 실행(workflow_dispatch)한다. 이 세션 환경에서는 사용자
   PAT로 GitHub API를 호출하면 403이 나므로, `add_repo`(access: "push")로 레포 접근을 먼저
   붙인 뒤 `gh api -X POST repos/.../actions/workflows/generate-coin-pages.yml/dispatches -f ref=main`
   을 쓴다. 실행 완료까지 확인하고 `coins/coin-{slug}.html`과 `sitemap.xml` 반영 여부를 보고한다.
9. **마무리 안내**: 모바일 확인 항목(상세페이지 접속, 앞·뒷면 이미지, 목록 순서), 임시값(프리미엄 등),
   `verified: false` 스펙 확인 필요 여부, 토큰 폐기 권장(저장하지 않음)을 알려준다.
